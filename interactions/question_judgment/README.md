# The Question-Judgment Interaction — why it's built this way

Read `interactions/README.md` first for the Interaction pattern itself; this
file is the "why" for one specific interaction: the judgment calls a model
makes about which follow-up questions deserve to exist and how urgently.

## 1. Mission tie-in

This interaction's objectives derive from `system/mission.md`'s three
purposes — help others understand me, enable me to tell my story, help me
understand myself — plus the owner's mission direction (owner's words,
2026-08-11):

> "honor and increase the value of your life and your relationships — hold
> them up, cherish them, realize how impactful they are in your life."

**The mission test.** A candidate question serves at least one of the three
purposes or it is the wrong question. This is the single admission gate —
every judged candidate is checked against it before priority or penalties
are even considered.

**Serving more than one purpose.** The three purposes are not competing
lanes to balance — they are lenses on the same material, and a candidate
that serves more than one at once is doing more work than a candidate that
serves only one. A question that surfaces a scene AND names a self-pattern
AND deepens a relationship is not "three-for-one luck" — it is what a
well-aimed question looks like, because a real moment in a real life is
never only one thing. This is this interaction's primary signal for the
top of the priority band (see `prompt/behavior.md`'s priority vocabulary)
— it is not a fourth mission purpose, and it is a different idea from
`system/mission.md`'s Convergence Principle (see below): a candidate
serving exactly one purpose is not penalized for it, plenty of good
questions are one-purpose, but a candidate serving two or three, each with
real evidence behind it, has earned the higher end of the band.

**How this interaction honors `system/mission.md`'s Convergence Principle**
(ADR 0006, v163 — the loop must work without us; not to be confused with
the "serving more than one purpose" idea above, which is this
interaction's own priority signal, not the mission-wide principle). Two
tiers, one mechanism, and this interaction is one of the concrete
instances ADR 0006 names outright ("see the decisions-feed-the-loop and
question-judgment interaction work"):

- **Floor — JUDGE mode is autonomous.** Every generated candidate is
  judged at capture with no human required; a vault that never opens a
  review surface still converges to well-judged, well-prioritized
  candidates over time. Nothing about this interaction's floor behavior
  depends on the owner ever looking at a verdict.
- **Accelerator — RUBRIC-EDIT mode consumes the owner's decisions as
  signal, never as a dependency.** The weekly pass reads which judged
  candidates the owner promoted, dismissed, or deferred (and why) and
  turns that into one bounded rubric amendment. An owner who never
  reviews anything still gets the floor's convergence; an owner who does
  review speeds up the same convergence, they do not unlock a different
  one. This is the concrete mechanism the follow-up
  "decisions-feed-the-loop" PR wires the runtime for — this PR ships only
  the RUBRIC-EDIT prompt template and the declared learned-amendments slot
  (see §4 below).

## 2. What judgment is, in this system

Every candidate follow-up question the system could ever ask a person is
generated by a model (the classifier extracting from a fresh source, the
research expander building a neighborhood, a future generation path not yet
written) and then judged: is it worth asking, how urgently relative to
everything else waiting, and — for the deterministic layer,
`question_candidates.check_quality` — does it commit any of a known set of
craft mistakes. Before this interaction, the criteria a model judged by were
scattered and truncated: `system/classify_story.py`'s prompt read
`research.md`'s craft doctrine and cut it off at 3000 characters — mid-way
through §1's numbered essentials — and `system/research_expand.py`'s prompt
read the same file and cut it to 800 characters, which in practice held
only the document's header and the AI-privacy paragraph. Zero craft
methodology was actually reaching either generation path. Priority-setting
was a single unexplained sentence ("set priority 0.4–0.95") with no
description of what evidence should put a candidate at which end.

This interaction makes the judgment criteria one reviewable, versioned
artifact instead: `prompt/behavior.md` — loaded whole, never truncated, by
every generation path via the one authoritative loader,
`system/question_judgment.py`.

## 3. Research basis

`system/research.md` §1 ("Question Design — the essentials") is the
scholarly source — eleven numbered essentials drawn from oral-history
canon (Morrissey's two-sentence rule), memoir craft (Karr's sensory
"carnality"), narrative-identity research (McAdams' five-slot scene
probe and the action↔identity ladder), and introspection research
(Eurich's why-produces-confabulation finding, the memory-reconsolidation
literature on restating an account as fact). `prompt/behavior.md`
RESTATES these eleven essentials in behavior-contract form — numbered
identically to §1 so the two documents can be read side by side — and
adds two things research.md intentionally leaves to product judgment: a
priority vocabulary (what evidence justifies scoring a candidate near
0.4 vs near 0.95) and a penalty vocabulary that mirrors
`question_candidates.check_quality`'s flags exactly, so a human reading a
judged verdict and a human reading a `check_quality` result are reading
the same language. Per the contract's binding facts: research.md stays
the scholarly source (citations, evidence strength, competitor
post-mortems); this interaction's `prompt/behavior.md` becomes the
*operational* authority the model actually reads — doc IS prompt, so
drift between "what we tell reviewers we do" and "what we actually send
the model" is now structurally impossible.

The quality-profile loop (`system/quality_profile.py`) is the other
research anchor worth naming here: it scores answered questions
retroactively for richness and feeds a weekly-aggregated profile back
into generation prompts as personalization hints. This interaction's
judgment rubric is what a model is checked against at judgment time;
the quality profile is what the system learns from answers *after* a
judged-and-asked question actually gets a response. The two are
independent signals today — this PR does not wire them together — but
future recalibration passes (see §4, the learning architecture) are the
natural place they'd meet.

## 4. Owner decisions (ratified 2026-08-14)

- **Tier guide.** `role.worker` (per-candidate judging — the high-volume,
  low-stakes call: is this one question worth asking) is a **medium**
  capability tier. `role.planner` (the weekly rubric edit and the rare
  full-ledger recalibration — low-volume, high-stakes, changes behavior
  for every future judgment) is a **high** capability tier. These name
  capability tiers, not vendor products — see `interaction.yaml`.
- **No router.** This interaction never receives free-form inbound
  messages; it only ever judges a candidate it was handed or edits a
  rubric it was handed. There is no out-of-scope input to classify or
  deflect, so `router/` is intentionally absent (see
  `interactions/README.md`: "an interaction may omit `router/`... if it
  doesn't need it").
- **Models are seated only after passing `evals/`.** No default seat ships
  with this PR — see §6.
- **Learning architecture.** Score once, at capture (the per-candidate
  JUDGE mode, every time a candidate is generated). A weekly pass reads
  the week's deltas (which judged candidates got promoted, answered, or
  rejected) plus a distilled summary of prior learned amendments, and
  makes exactly ONE bounded, auditable edit to the learned-amendments
  file — never a rewrite, never more than
  `knob.weekly_edit_max_chars` characters, always with an evidence line
  citing what prompted it. A quarterly pass re-examines the full
  candidate ledger for drift the weekly increments might have missed.
  **This PR declares the slots only** — `state/question_judgment/learned.md`
  is registered in `system/vault_contract.json` as vault data (never a
  framework file — a person's own accumulated judgment amendments are
  theirs, not something the framework ships), and the loader treats a
  missing file as simply empty. The RUNTIME that actually writes to it
  is the follow-up "decisions-feed-the-loop" PR's job, not this one's.

## 5. How it's built

- **Behavior contract**: `prompt/behavior.md` — the load-bearing file, the
  rubric itself, both the prompt sent to the model and the document the
  owner reviews and amends.
- **Context recipe**: `context/manifest.md` — the deterministic assembly
  order (identity → behavior → learned → examples → profile-distillate →
  turn_instructions) and token budgets, matching `interaction.yaml`'s
  `budget.*` keys.
- **The loader**: `system/question_judgment.py` —
  `load_judgment_rubric()` is the one authoritative place every
  generation path reads the judgment context from. It assembles
  `prompt/behavior.md` plus `state/question_judgment/learned.md` (empty
  when absent — no vault has amendments yet), and degrades to the
  pre-migration truncated `research.md` injection ONLY when the
  interaction directory itself is missing (a vault mid-upgrade, running
  against an older framework snapshot that predates this interaction).
  `system/classify_story.py`'s `build_prompt` and
  `system/research_expand.py`'s expansion prompt path both call this
  loader now; the `research[:3000]` and `research_notes[:800]`
  truncations that used to sit between the classifier/expander and
  `research.md` are gone.
- **Durable state**: `state/question_judgment/learned.md` — declared in
  `system/vault_contract.json`, not written by anything in this PR (see
  §4).

## 6. How to eval

`evals/` is the model contract, following the same four-part shape as
`interactions/conversation/evals/`: `lints.yaml` (deterministic —
`prompt/behavior.md` carries numbered rules, a judge verdict parses as the
compact JSON the turn-instructions template specifies, a rubric-edit
amendment never exceeds `knob.weekly_edit_max_chars`), `rubrics.md` (a
binary yes/no judge question per hard rule, 1:1 with `prompt/behavior.md`),
`goldens/` (fixture format documented in `goldens/README.md`; committed
fixtures land with the wiring PR, not this one), and `personas/` (a README
stub — the persona set is designed alongside the wiring PR once real judged
output exists to model against).

No engine reads `evals/lints.yaml` yet (mirrors the conversation
interaction's own bootstrap PR) — this PR ships the model contract as
data; a future harness run, and a `evals/roster.md`-style seating record,
is what actually seats a model in `role.worker` or `role.planner`. Until
that harness exists and a model passes it, this interaction has no
default seat, exactly as `interactions/README.md`'s pattern requires.
